採用HP 制作キットの使い方 （v1.0 β版）

採用HP（TOP と下層ページ）を、毎回同じ土台と同じ検査で作るためのキットの手引きです。AI やターミナル（文字でパソコンに指示を出す画面）に慣れていなくても進められるよう、「あなたがすること」と「AI がすること」を分けて書いています。採用LP は別のキット（spinova-lp-kit）です。

このキットを使う前に（必ず守ってください）
  1. このキットとマニュアルは、SPINOVA の制作のためだけに使ってください。ほかの仕事や個人の制作には使わず、人にも渡さないでください。
  2. キットの中身（手順書・道具・土台）は、自分で書き換えないでください。AI に頼んでも書き換えません。直したい所は、責任者へ伝えてください。
  3. キットで作ったサイトには、このキットで作られたことが分かる目印（版と印）が入ります。
  4. ヒアリングシートにある認証情報（FTP・WordPress の ID とパスワード）は、AI に読ませない・貼らないでください。

1このページについて

結論：キットをパソコン（Mac・Windows）に置き、AI のアプリでキットのフォルダを開いて案件を渡すと、AI が採用HP を作ります。最初に見せるのは TOP だけ。TOP の OK が出てから下層ページを作ります。あなたの仕事は「選ぶ・見て直しを伝える・OK を出す・送る」です。

できること

  • ヒアリングシートから、TOP と下層（私たちについて・事業内容・会社概要・お問い合わせ。シートの構成に合わせて増減）を作る
  • リンク切れ・はみ出し・最小の文字・メニュー・読みやすさ・改行などを道具で検査する
  • 合格し、承認がそろったものだけを公開する（版ごとの URL）

作らないもの

  • 採用ページ（標準は採用LP へのリンク。シートの「採用情報の扱い」で決めます）
  • WordPress への移行の手順（HP 版はまだありません。11章）

結論：あなたの手が変わるのは、公開の待ち時間が短くなったことと、新しいヒアリングシートをそのまま渡せるようになったことです。作り方の大筋は同じです。

写真に文字を重ねる所文字と写真の重なりを「意図したもの」として通すときは、AI が画像を見せてあなたに聞いてから印を付けます（新しく始める案件から）

3LP キットとの違い

結論：進め方の大筋（シートを読む → 要件を整理 → 参考サイトを分析 → 最初の画面を見せる → 検査 → 承認 → 公開 → 修正）と、あなたの役割・守ることは、採用LP キットと同じです。違うのは作るものの形（1ページのスワイプ型か、TOP と下層の複数ページか）と、それに合わせた検査と道具の範囲です。

項目採用LP キット採用HP キット（このキット）
作るもの採用LP（1ページ）。標準は縦スワイプ型（1回の操作で1画面ずつ進む形）採用HP（TOP と下層ページ）。ふつうに上下へスクロールする形
ページ1ページの中に画面を並べるTOP と下層（シートのサイトマップに合わせて増減）。ヘッダー・フッター・メニューは TOP が元で、道具が全ページへ写す
ヒアリングシートLP のシートHP のシート（新しい様式・前の様式とも読める）。LP のシートを読む道具では読めない
最初に見せるもの1枚目（最初の画面）を参考サイトと並べて見せ、OK のあと全体を作るTOP の最初の画面（FV）を参考サイトと並べて見せ、OK のあと TOP を仕上げて先方へ出す。方向の OK のあと下層を作る
採用情報LP そのものが採用ページ標準は採用ページを作らず、採用LP へのリンクにする（シートの指定で決める）
動き動きの見本帳から選ぶ。最初の画面の動画（FV動画）は責任者が別に作る見本帳は無い。土台の動き（ふわっと出る・英字の見出しのせり上がり・ローディング など）から選び、足りない分だけ足す
検査の大きさ4サイズ。ページ送りや、1画面に収まるかも見る先方用の公開の前は4サイズ（スマホ 360・375・390 と PC 1440）。時間のかかる検査（文字の読みやすさ・絵の見切れ・改行）はスマホ 390 と PC 1440 の2サイズ。社内の確認用の公開は 390 と 1440 の2サイズだけ。1画面に収める検査は無い
検査の時間約7〜8分公開の前の速い検査は数秒。社内の確認用の公開は5ページで約15〜25秒。先方用の公開は初回の全ページで約3分、2回目からは変わったページだけを時間のかかる検査にかける
修正の比較画像同じ。スマホの1サイズで、直した所を「修正前｜修正後」で切り出し、1枚に縦に積む。AI への指定の仕方も同じ
公開同じ。社内の確認用（GitHub Pages）→ 先方用（Cloudflare Pages の版ごとの URL）。前の版の URL は上書きしない。HP では、責任者が「検査とばせ」と言った版だけ、時間のかかる検査を省いて出す「急ぎの公開」がある（9章）
確認の手助けいろいろな幅で見るクオリティチェッカー・別の AI による見直し（レビュー役）・困ったときに送る作業記録の ZIP別の AI による見直し（レビュー役）はある。いろいろな幅で見るチェッカーと作業記録の ZIP はまだ無い。全ページを PC・スマホ各1枚の画像で見る
見た目の検査の ✕同じ。リンク切れなど事実の誤りは止める。見た目（はみ出し・見切れ・重なり・読みやすさ・改行）は止めずに「要確認」として、案を並べた画像で聞く
WordPress への移行指示文があるまだ無い（11章）

7案件ごとの流れ：TOP の初稿を出すまで

結論：あなたがするのは「案件を渡す」「質問に答える」「TOP を見て直してほしい所を伝える」「OK を出す」「先方へ送る」です。作る・調べる・検査する・公開するのは AI です。確認はそのつど来るので、制作中は返事ができるようにしてください。

案件ごとに、新しいチャットを作ってください。1つのチャットで複数の案件を進めると、AI が案件どうしを取り違えます。修正もその案件のチャットで続けます。

最初の一言（コピーして AI に送る）

新しい HP の案件を始めてください。
担当案件：〔担当案件の URL か、ヒアリングシートの場所を書く〕
進め方の選択・公開・クライアントへの送信は、私が決めます。

  • 下層は中身を作る前の仮ページのまま出す（仮ページは時間のかかる検査を省く）。共有文面に「今回は TOP のみ」「仮の所」を書く

ヒアリングシートの読み方

シートは、AI がシートを読む道具（tools/dump_hp_sheet.py。シートを要件整理に使う形で書き出す道具）で読みます。Google のシートは xlsx に書き出してから読みます。LP のシートを読む道具では、HP のシートは読めません。

新しい様式

  • タブは「基本情報」と「採用HP(提出用)」の2つ。原稿のタブはありません
  • 基本情報の 1〜17行は LP と同じ。19行目からが HP の項目（会社名・所在地・事業内容・HP の種類・新規かリニューアルか・今のサイトの URL・業種・採用情報の扱い・採用ページの URL・ドメイン）
  • 「採用HP(提出用)」は、カラー・ページ・セクション・文言・スクショ・参考 URL・参考にしたいポイント・補足

前の様式

  • タブ「概要」＋ページごとのタブ（10枚前後）
  • 概要のタブは丸ごと読みません（認証情報の行があるため）。ほかのタブを行ごとに書き出し、ページの名前のタブから下層の一覧の候補を作ります

読まないもの・別の様式

  • 基本情報の 15〜17行（FTP・パスワード・サーバー）は、道具も AI も読みません。問い合わせの通知先は「ある・無い」だけ
  • どちらでもない様式（先方の独自の様式）は、道具が「読めない」と出し、AI が手で書き出します

クオリティを上げるコツ（参考と離れていると感じたら、コピーして AI に送る）

デザインテイストが参考サイトと離れているのでもう一度デザインDNA分析をやり直してください。分析が完了したら作業前に分析結果を言語化してまとめてください

まとめが届いたら中身を確かめ、「この分析のとおりに作り直してください」と送ります。言葉にさせてから作らせると、次の版の質が上がります。

8下層ページと作りの決まり

結論：先方から TOP の方向に OK が出たら、「下層を作って」と伝えます。ページはシートのサイトマップに合わせます。作るときの決まりは AI が手順書で守ります。あなたは、下の要点に外れていないかを画像で見てください。

下層ページ

  • ヘッダー・フッター・メニューは TOP が元で、道具が全ページへ写します。メニューとフッターには「トップ」が入ります。
  • 同じ役割の見出し・ボタン・表は、ページの間でそろえます。同じ写真・同じ構図は使い回しません。
  • 「リッチな動きに」と言われたら、まず土台の動き（ふわっと出る・英字の見出しのせり上がり・メニュー・ローディング・ボタン）から選び、足りない分だけ足します。参考に無い動きは足しません。
  • お問い合わせフォームは見た目までです。送信の仕組みは WordPress への移行で入ります（11章）。
  • 確定の文が無い所は仮の文にし、提出のときに「仮の所」として伝えます。

作りの決まり（要点）

改行・余白

  • 文節で折る。強調の句・社名・数字と単位・電話・〒番号は途中で折らない
  • 余白は5段階：行間 ＜ 段落 ＜ 本文とボタン ＜ 見出しと本文 ＜ まとまりの間
  • スマホの余白は PC の約6〜7割
  • 番号と項目の間は、項目どうしの間より近く

写真・FV

  • FV を見せる前に本番の写真を入れる
  • ヘッダーは写真に重ねない（参考が重ねているときだけ）
  • 写真の上の文字は白・顔に掛けない
  • AI の写真は手を原寸で数える。スマホで顔・頭が切れていないか

見出し・強調

  • とりあえず強調をしない（太く大きく・色文字・太い下線を反射で足さない）
  • シートに無い記号・飾り文字を足さない。文字に filter をかけない
  • 大きな文を横いっぱいにしない（1行 20〜30字まで）
  • 「・」「※」で始まる文は、2行目の頭をそろえる（ぶら下げ）
  • 明るいキーカラーは文字ではなく面に。（ ）の中は 85% の大きさ

ほかに：ホバーの下線は文字のすぐ下／英字の書体の数字の高さをそろえる／「！？」の傾きと高さを拡大して確かめる／マウスに追う動きは PC だけ／横に流すカルーセルは、フェードで入れ替える形も選べる。最小の文字は 13px。

9提出前のチェックと公開

結論：公開は公開の道具（tools/publish.sh。検査・承認の確認・公開・照合をまとめて行う道具）だけで行います。検査に合格し、その版の承認の記録があるときだけ公開されます。AI は公開の前に手元で検査を通し、✕ をまとめて直してから1回だけ公開します。公開の完了は待たずに、先に画像で報告します。

確かめる段は3つ（A・B・C）

A　道具が判定

  • 止める（事実）：リンク切れ・メニューの開閉・電話と〒の折れ・仮の文言など。✕ が0になるまで AI が直す
  • 聞く（見た目）：はみ出し・文字の見切れ・最小の文字 13px・写真との重なり・読みやすさ・絵の見切れ・改行・文字のぼかし。止めずに「要確認」になり、切り抜き画像と「今｜案A｜案B」を並べた1枚で聞かれる → あなたが選ぶ

B　AI が見て直し、責任者が画像で承認

  • 改行・余白の段階・写真・ページ間のそろい・参考サイトらしさ
  • 全ページを PC・スマホ各1枚の画像で見る

C　責任者だけが判断

  • 見た目の質・写真の選び方
  • iPhone の実機で触ったか（見ていなければ「未確認」）
  • 提出・公開してよいか

公開の前に AI がすること

  1. 手元で速い検査を通す

    組み立て・CSS の散らかり・リンク切れ・飛び先・読み込みの版の印・公開用の複製を、数秒で見ます（検査の道具 run_all.sh の --fast。速い検査だけを回す指定）。直したページは画面の検査も通します。公開の門を「検査の代わり」に使いません。

  2. ✕ は全部まとめて直してから、公開を1回だけ

    速い検査は ✕ を全部まとめて出します。1件直しては公開し直す、をしません。速い検査に ✕ があると、時間のかかる画面の検査の前に止まります。

  3. 公開は裏で流し、完了を待たない

    小さな直しは、直した所の画像と報告で先に終えます。URL は出たら後から届きます。

公開の流れ

  1. 確認用で先に見る（社内）

    確認用の GitHub Pages に出して社内で見ます。了承は要らず、リポジトリや Pages が無ければ道具が作ります。検査は画面の大きさ2つ（390・1440）で、5ページで約15〜25秒です。いきなり先方用を出しません。

  2. 責任者の OK を、版ごとに記録する

    責任者がチャットで「OK、公開に進んで」と伝えたときだけ、AI が承認の行を書きます（版ごとに1行。前の版の OK は使い回しません）。

  3. 公開する

    版ごとの URL（v1・v2 …）で公開されます。前の版の URL は上書きされません（責任者が上書きを指示したときだけ、先に一言伝えてから上書きします）。公開のあと、道具が公開された全ファイルを手元と照合します。

  4. 共有文面を送る

    AI が下書きを作ります。書くのは URL と「仮の所・通常と変えた点」だけ。送るのはあなたです（AI は Slack を送りません）。

検査の時間・やり直し・急ぎの公開

  • 時間の目安（試しの5ページ・手元での計測）：速い検査は数秒。確認用の公開は約15〜25秒。先方用の公開は、初回が全ページで約3分。2回目からは、前の合格から変わったページだけを時間のかかる検査にかけます（写真の差し替えは、その写真を使うページだけ。CSS やヘッダーの直しは全ページ）。小さな直しは1回の公開にまとめます。
  • 合格の使い回し：同じ中身で合格していれば、2回目の公開は検査を省き、承認・公開・照合だけを行います。1バイトでも違えば検査からやり直します。
  • 送信だけのやり直し：検査に合格したあとに送信（GitHub への push など）が失敗したら、AI が同じ公開に「送信だけやり直す」指定（--retry-push）を付けて流します。検査はやり直しません。
  • 固まったとき：1ページ・1画面の大きさごとに時間の上限（既定 90秒）があり、超えると「✕ 固まった：ページ・サイズ」と出して止まります。外側で時間を切ることはしません。
  • 要確認：見た目の要確認が出ると、公開せずに止まります（✕ ではありません）。画像を見て案を選ぶと、AI が直し、「答えた」指定（--asked）を付けて流し直します。答えた所は、次の版でも聞き直しません。写真に文字を重ねるなど「意図した重なり」の印も、あなたに聞いてから付けます。
  • 急ぎの公開：責任者が「検査とばせ」「すぐ出して」と言った版だけ、時間のかかる検査を省いて出します（急ぎの公開の指定 --quick。ほかの検査・承認・公開後の照合はいつも通り）。省いた分は、次の版を出すときにまとめて検査します。本番の URL には使えません。手で公開することはしません。

10クライアントから修正が来たら

結論：修正の指示（Slack のスレッドの URL など）を、その案件のチャットに貼るだけです。AI はまとめて直し、直した所を見せ、版を上げて公開し、返信文の下書きと比較画像を渡します。

修正が来ました。修正時.md の手順で進めてください。
修正の指示：〔Slack のスレッドの URL か、指示の文を貼る〕
  • 先方へ出した後の直しは、必ず版を上げます（v1 → v2）。前の版の URL は残るので、先方が見比べられます。
  • 指摘された所と同じクラス・同じ型の所を全部洗い出して、まとめて直します（言われた1か所だけを直しません）。
  • 直している間は、直した所を撮って見せるだけです。検査は公開の前に1回。急ぎのときは、責任者の指示で急ぎの公開（9章）にできます。
  • 比較画像は毎回1枚：スマホの幅の1サイズで、直した所を「修正前｜修正後」で切り出し、全部を1枚に縦に積みます（多いときだけ道具が2枚に分けます）。直した所ごとに、見る所と数値を赤の一文で添えます。PC でしか見えない直しのときだけ、PC の1サイズにします。画像は公開したあとの URL 同士で作ります。
  • AI への指定の仕方は LP キットと同じで、ページと直した所を指定します（比較画像の道具 before_after.mjs の --focus。赤の一文は --note）。あなたが指定を書く必要はありません。
  • 渡す順番は「返信文の下書き → すぐ画像」。送るのはあなたです。
  • 先方の文言は、Slack・シートの原文から写します（転送文・要約から写しません）。
  • 返信の下書きには、指示の番号ごとに「どこを・どう変えたか」を書きます（「反映しました」だけにしません）。
  • 社内の見た目の直しが3回目に入っても方向が合わないときは、AI が参考サイトの分析からの作り直しを提案します。
  • 先方の指摘は、種類ごとに記録してためます。キットの改善になるものは、案件の区切りで責任者へ1行で伝えます。

12困ったとき

検査で止まった

✕ の行に、ページ・画面の大きさ・理由が出ます。AI に「✕ を全部まとめて直して、同じコマンドを流し直して」と伝えます。検査を通すために、除外の指定で消すことはしません。

「FV の確認がまだ」で止まった

最初の画面（FV）の OK が、まだ記録されていません。AI に並べた画像を出してもらい、見て OK を伝えてください。TOP の検査は、この前でも通ります。

「要確認」で止まった

✕ ではなく、見た目を人が決める所です。届いた画像（今と案を並べた1枚）を見て、どれにするかを答えます。答えたあと、AI が続きから公開に進みます。

「✕ 固まった」と出た

ブラウザが応答しなくなったページと画面の大きさが出ます。AI に「固まった所を確かめて、流し直して」と伝えます。同じ所で何度も出るときは責任者へ。

公開の送信で失敗した

検査には合格して、送信（GitHub など）だけが失敗した状態です。AI に「送信だけやり直して」と伝えます（検査はやり直しません）。

公開で止まった

「承認の行がありません」は、その版の責任者の OK がまだ記録されていない、という意味です。「もう公開しています」は、同じ版へ出し直そうとしたときです（次の番号で出します）。

キットがおかしい

版を確かめる道具（tools/version.sh）で、キットの版と、キット本体が書き換わっていないかが分かります。不具合・足りない所は、AI に直させず、責任者へ伝えてください。

β版で気づいたこと

使いにくい所・止まった所・手順書と違った動きは、最初の案件のうちに責任者へ返してください。AI に「キットへの改善メモを1行にまとめて」と頼むと、案件の記録から書き出します。

13守ること

  1. 顧客の情報を外に出さない

    ヒアリングシート・写真・ロゴ・参考サイトの複製を、キットの外やほかの案件へ持ち出しません。認証情報は AI に読ませません。

  2. 公開と送信は人が承認する

    公開・クライアントへの送信・Slack への投稿は、あなたと責任者が決めます。AI は下書きまでです。

  3. 「OK」は人が出す

    承認の記録は、責任者がはっきり OK を伝えたときだけ書かれます。AI の判断では書きません。

  4. 事実を足さない

    シートに無い電話・住所・数字・実績を、AI に作らせません。先方の文言は言い換えません。

  5. キットを書き換えない・再配布しない

    手順書・道具・土台は直しません。キットと、このページのダウンロードのリンク・パスワードを、ほかの人に渡しません。
